The NameNode stores metadata such as the directory tree of all files in the file system,

 Components of Hadoop

4.
 name node, data node, standby name node, zookeeper, jornal node 

name node
the master node that stores metadata information for all files and directories in hdfs.
location of the data blocks and manages data node.
does not store in actual data.

 data node
the slave node responsible for storing actual data in hdfs and name node manages the data node.
 every 3 seconds, data node sends heart beat to name node.


Standby Namenode:
In the event of a failure of the Primary Namenode, the Standby Namenode can take over to ensure continuity of HDFS operations.

JournalNodes:

JournalNodes are a set of separate daemons responsible for storing and managing the edit logs.
Both the active and standby NameNodes send their edit logs to the JournalNodes for durability.
Each JournalNode maintains a copy of the edit log.

zookeeper
Apache ZooKeeper is a distributed coordination service.

ZooKeeper is used for storing and managing configuration information in a distributed environment.

where distributed systems require coordination, synchronization, and management of configuration information
ZooKeeper distributed coordination service, ensuring that tasks are executed in a coordinated manner across a cluster of machines.
If the active master fails, ZooKeeper helps in electing a new master to maintain high availability.
ZooKeeper itself is designed to be highly available and fault-tolerant.

9.
fs image, edit log, under replication, over replication in hadoop


FS Image
FS Image in name node stores the meta information of every transaction about the data nodes.


EditLogs
Editlog is a transaction log that records the changes in the HDFS file system or any action performed on the HDFS cluster such as
 addition of a new block, replication, deletion etc.

 Edit Log is a temporary file which helps checkpointing for every one hour which is the default time.
Secondary name node helps for checkpointing.



 Under replication in data nodes
As default replication factor is 3, if any of the nodes goes down then, 
the blocks in that node has only two replication (less than 3) in 
 other nodes which we call as under replication.



Over replication in data nodes
If any of the dead node is marked as done after grace time, a new node is created to 
take care of 3 replication. In such a situation, if all of a sudden of 
the dead node comes alive then, it becomes 4 replication totally – which is 
called over replication.

10.
split brain scenario and speculative execution in hadoop


Split brain scenario
If dead node becomes active and start write the edit logs to the Journal node and 
also the recent active name node does the same is called split brain scenario.
Zookeeper will send a fencing program to stop the write so we don’t face the
 split-brain scenario.


Speculative execution in Hadoop
In Hadoop during Speculative Execution, a certain number of duplicate tasks are launched.
 On a different slave node, effect of slow running tasks by having backup that can potentially finish faster. if a speculative execution task compleates first. its result are used and the redundant(repeated) tasks are killed.
this helps improve overall job completion time in hadoop cluster.


Enabling & Disabling of Speculative execution - 

Speculative execution is enabled by default. You can disable speculative execution for mappers and reducers in mapred-site.xml as shown below:

<property>

<name>mapred.map.tasks.speculative.execution</name>

<value>false</value>

17.
difference between regular file system and hadoop filesystem

Regular FileSystem: 
In regular FileSystem, data is maintained in a single system. If the machine crashes, 
data recovery is challenging due to low fault tolerance

HDFS:
 Data is distributed and maintained on multiple systems. If a DataNode crashes, 
data can still be recovered from other nodes in the cluster.

18.
yarn components in hadoop


YARN components:

Resource Manager - It runs on a master daemon and controls the resource allocation in the cluster.
Node Manager - It runs on a slave daemon and is responsible for the execution of tasks for each single Data Node.
Application Master - It maintains the user job lifecycle and resource requirements of individual applications. It operates along with the Node Manager and controls the execution of tasks.
Container - It is a combination of resources such as Network, HDD, RAM, CPU, etc., on a single node.

2.
mapreduce in hive

 To handle large-scale data processing.

 two primary steps: the Map phase and the Reduce phase.
  
Map Phase:
 In this initial step, input data is divided into smaller chunks or partitions and distributed across multiple nodes in a cluster.
  Each node processes its portion of data using a 'map' function. The 'map' function takes the input data and transforms it into intermediate key-value pairs.

Shuffle and Sort: 
After the Map phase, the intermediate key-value pairs are shuffled and sorted based on their keys. This process brings together all values associated with the same key, preparing the data for the next step.

Reduce Phase: 
In this phase, another function called the 'reduce' function is applied  to the sorted intermediate data.
 The 'reduce' function merges and aggregates the values associated with the  same key produced by the 'map' function.
 The output of the 'reduce' function is the final result of the MapReduce job.

Dividing the data into multiple chunks to ensure the query performance.

4.	Mapjoin:  

In Hive, a Map Join is an optimization technique used to perform a join operation

In map-side joins, the smaller table is cached in the memory while the large table is streamed through mappers. By doing so, 
Hive completes the joining at the mapper side only, thereby removing the reducer job.

disadvantage of map side join in hive
Hence it is not suitable to perform map-side join on the tables which are huge data in both of them

6.	Sort Merge Bucket Join:
Sort Merge Bucket (SMB) join in hive is mainly used as there is no limit on file or partition or table join. SMB join can best be used when the tables are large. In SMB join the columns are bucketed and sorted using the join columns. All tables should have the same number of buckets in SMB join.
Bucketing and sorting the data can improve the performance of join operations by reducing the need for shuffling

It would help to join Bucket to Bucket of 2 tables should have
 equal number of buckets.

-- Enable map-side or bucketed map join optimization if necessary
SET hive.auto.convert.join=true;
SET hive.auto.convert.join.noconditionaltask=true;

-- Perform Sort-Merge Bucket Join
SELECT *
FROM table1
JOIN table2 ON table1.common_key = table2.common_key;

22.
 Purge option in hive

The hive DROP TABLE statement comes with a PURGE option.
 In case if the PURGE option is mentioned the data will be completely lost and cannot be recovered later but 
if not mentioned then data will move to . Trash/current directory.

If Trash is configured by setting true to hive.warehouse.data.skipTrash property, dropping an Internal table moves the actual data to users .Trash directory, you can recover this data post drop.

DROP TABLE IF EXISTS employee PURGE;
You can use PURGE option to not move the data to .Trash directory, the data will be permanently removed and it can not be recovered.

Q.  what is scope in python

All objects in Python have a scope. Scope is the block of code where the variable is accessible


There are mainly two types of scopes in Python

Global Scope:

Variables defined outside any function or class have a global scope.

global_variable = 10

def my_function():
    print(global_variable)

my_function()  # Output: 10




Local Scope:

Variables defined inside a function have a local scope.

def my_function():
    local_variable = 5
    print(local_variable)

my_function()  # Output: 5

# This would raise an error because local_variable is not accessible outside the function.
print(local_variable)




Enclosing Scope (non-local):

This scope applies to nested functions, where a function is defined inside another function.

def outer_function():
    outer_variable = 20

    def inner_function():
        print(outer_variable)

    inner_function()

outer_function()  # Output: 20

Q.
what is data skew ness

where the data being processed is not distributed evenly across partitions. , we call the data “skewed.” In spark


Causes of Data Skewness
Some keys may have a high number of occurrences (hot keys), causing a skewed distribution of data across partitions.

example, the default Hash Partitioning strategy might cause data skewness if certain keys hash to the same partition.

where a large dataset is joined with a small dataset on a non-unique key.

 Similar to join operations, GroupBy operations can also cause data skewness when certain keys have many more values than others.


Handling Data Skewness in Apache Spark
Although data skewness can impact your Spark application’s performance

Custom Partitioning
 For example, range partitioning can be more effective when dealing with numeric keys.

Salting: Salting is a technique where a random value (salt) is appended to the key, which helps distribute the data more evenly across partitions. This can be particularly useful when dealing with hot keys.

Avoid GroupBy for Large Datasets: When possible, avoid using GroupBy operations on large datasets with non-unique keys. Alternatives such as reduceByKey, which performs a combine operation locally on each partition before performing the grouping operation, can be more efficient.


. Salting Technique
Salting is a useful technique when certain keys (hot keys) in your data have a high number of occurrences, which results in skewness. The idea is to add a random number (salt) to the key, so that the records with the same key are now spread across multiple keys.

Let's see how to apply salting in Spark with Scala:

val spark: SparkSession = ...

// Assume we have a DataFrame with data skewness
val skewedDF: DataFrame = ...

// Define a UDF to add salt
val addSaltUdf = udf((key: String) => key + "_" + Random.nextInt(100))

// Add salt to key
val saltedDF = skewedDF.withColumn("key", addSaltUdf(col("key")))

// Now you can perform operations on saltedDF without data skewness issue
2. Custom Partitioning
If the default partitioning strategy in Spark doesn't distribute your data evenly, you can consider implementing a custom partitioning strategy. Let's take an example of using range partitioning:

val spark: SparkSession = ...

// Assume we have a RDD with data skewness
val skewedRDD: RDD[(Int, String)] = ...

// Custom range partitioner
val customPartitioner = new RangePartitioner(10, skewedRDD)

// Apply the custom partitioner
val partitionedRDD = skewedRDD.partitionBy(customPartitioner)

// Now you can perform operations on partitionedRDD without data skewness issue
3. Splitting Skewed Data
If you can identify the skewed keys, you can split the skewed data and non-skewed data into two separate RDDs/DataFrames and process them separately.

val spark: SparkSession = ...

// Assume we have a DataFrame with data skewness
val skewedDF: DataFrame = ...

// Skewed keys
val skewedKeys = Seq("key1", "key2", "key3")

// Split the data
val skewedData = skewedDF.filter(col("key").isin(skewedKeys: _*))
val nonSkewedData = skewedDF.filter(!col("key").isin(skewedKeys: _*))

// Process skewedData and nonSkewedData separately
Remember, the right strategy to handle data skewness depends on the specifics of your data and application. Applying these strategies correctly can significantly improve the performance of your Spark applications. Q. what is dataframe

In Spark, DataFrames are the distributed collections of data, organized into rows and columns. Each column in a DataFrame has a name and an associated type. DataFrames are similar to traditional database tables, which are structured and concise. We can say that DataFrames are relational databases with better optimization techniques.

Spark DataFrames can be created from various sources, such as Hive tables, log tables, external databases, or the existing RDDs. DataFrames allow the processing of huge amounts of data.


Features of DataFrames
Some of the unique features of DataFrames are:

Use of Input Optimization Engine: DataFrames make use of the input optimization engines, e.g., Catalyst Optimizer, to process data efficiently. We can use the same engine for all Python, Java, Scala, and R DataFrame APIs.
Handling of Structured Data: DataFrames provide a schematic view of data. Here, the data has some meaning to it when it is being stored.
Custom Memory Management: In RDDs, the data is stored in memory, whereas DataFrames store data off-heap (outside the main Java Heap space, but still inside RAM), which in turn reduces the garbage collection overload.
Flexibility: DataFrames, like RDDs, can support various formats of data, such as CSV, Cassandra, etc.
Scalability: DataFrames can be integrated with various other Big Data tools, and they allow processing megabytes to petabytes of data at once.

When it is mentioned that "the table is first materialized at the driver side and then broadcasted to the executors," it refers to the process of bringing a small DataFrame or dataset entirely to the driver program and then broadcasting it to all the executor nodes in a Spark cluster.

Here's a breakdown of the process:

Materialization at the Driver Side:

The term "materialization" refers to the process of collecting or loading the entire dataset into the memory of the Spark driver program.
This is typically done when the dataset (or table) is relatively small and can fit comfortably in the memory of the driver.
Broadcasting to the Executors:

Once the small dataset is materialized at the driver, it is then broadcasted to all the executor nodes in the Spark cluster.
Broadcasting involves sending a copy of the dataset to each executor's local memory. This is an optimization to avoid sending the same data over the network for each task.





    // Perform the broadcast join

Executor OOM---Yarn memory overhead

 
OutOfMemory at the Executor Level
Total executor memory = total RAM per instance / number of executors per instance

There are a few common reasons also that would cause this failure:

Inefficient queries

High concurrency

Incorrect configuration


1. Inefficient Queries
Example: Selecting all the columns from a Parquet/ORC table.

Explanation: Each column needs some in-memory column batch state. The overhead will directly increase with the number of columns being selected.

The Catalyst optimizer in Spark tries as much as possible to optimize the queries, but it can’t help you with scenarios like this when the query itself is inefficiently written.

Solution: Try to reduce the load of executors by filtering as much data as possible, using partition pruning(partition columns) if possible, it will largely decrease the movement of data.But there could be another issue that can arise in big partitions. You can resolve it by setting the partition size: increase the value of spark.sql.shuffle.partitions.

2. High Concurrency

Apache Spark Parallel Processing.

In case of an inappropriate number of spark cores for our executors, we will have to process too many partitions. All these will be running in parallel and will have their memory overhead; therefore, they need the executor memory and can probably cause OutOfMemory errors.

To fix this, we can configure spark.default.parallelism and spark.executor.cores and based on your requirement you can decide the numbers.


3. Incorrect Configuration
Each Spark Application will have a different requirement of memory.

There is a possibility that the application fails due to YARN memory overhead issue(if Spark is running on YARN). Therefore, based on each requirement, the configuration has to be done properly so that output does not spill on the disk. Configuring memory using spark.yarn.executor.memoryOverhead will help you resolve this.


e.g.

--conf “spark.executor.memory=12g”

--conf “spark.yarn.executor.memoryOverhead=2048”

or, --executor-memory=12g

+++ 17. Spark Broadcast Variables
===========================

Broadcast variables are read-only shared variables that are cached and available on all nodes in a cluster in-order to access or use by the tasks.

Use case
---------------
Let me explain with an example, assume you are getting a two-letter country state code in a file and you wanted to transform it to full state name, (for example CA to California, NY to New York e.t.c)

-> by doing a lookup to reference mapping. In some instances, this data could be large and you may have many such lookups (like zip code).


How does Spark Broadcast work?
-----------------------------------
	When you run a Spark RDD, DataFrame jobs that has the Broadcast variables defined and used, Spark does the following.

Spark breaks the job into stages that have distributed shuffling and actions are executed with in the stage.
Later Stages are also broken into tasks
Spark broadcasts the common data (reusable) needed by tasks within each stage.
The broadcasted data is cache in serialized format and deserialized before executing each task.
You should be creating and using broadcast variables for data that shared across multiple stages and tasks.

Note that broadcast variables are not sent to executors with sc.broadcast(variable) call instead, they will be sent to executors when they are first used

19. Apache Spark Architecture
Apache Spark also called master-slave architecture 
where the master is called “Driver” 
and slaves are called “Workers”. 

driver program
The driver program is the main program that runs the Spark application and creates a SparkContext.

spark context
spark context that is an entry point to your application, and

worker node
all operations (transformations and actions) are executed on worker nodes, and 

cluster manager
the resources are managed by Cluster Manager

Cluster Manager:

Spark can run on various cluster managers like Apache Mesos, Hadoop YARN, or its standalone cluster manager. 
The cluster manager is responsible for allocating resources and managing the distribution of tasks across the cluster.

Executor:

Executors are processes that responsible for executing tasks assigned to it by the Spark driver program.
They are launched on worker nodes in the cluster and communicate with the driver program.
Executors also manage the data stored in the cache and disk, and they handle shuffle operations
Each Executor is allocated a certain amount of memory and CPU resources when it is started,


Task:
A task is the smallest unit of work in Spark and represents a unit of computation.
Tasks are executed on individual executor nodes, and multiple tasks can run concurrently on a single executor.

21. DAG (Directed Acyclic Graph):

--> The DAG is “directed” because the operations are executed in a specific order,
--> and “acyclic” because there are no loops or cycles in the execution plan. This means that each stage depends on the completion of the previous stage,and  each task within a stage can run independently of the other.

-->At a high level, a DAG represents the logical execution plan of a Spark job.
--> When a Spark application is submitted, Spark translates the high-level operations (such as transformations and actions) specified in the application code into a DAG of stages and tasks.



The DAG allows Spark to perform various optimizations, such as pipelining, task reordering, and pruning unnecessary operations, to improve the efficiency of the job execution.

Q. DAG Scheduler
 the DAG Scheduler is responsible for transforming a sequence of RDD transformations and actions into a directed acyclic graph (DAG) of stages and tasks,
 which can be executed in parallel across a cluster of machines. The DAG Scheduler is one of the key components of the Spark execution engine.

Collection of Tasks means stage –

Q. PySpark Regexp_Extract()
----------------------------
In PySpark, we can extract a specific group from the strings based on the specified patterns using the regexp_extract() function.
 It returns the string that is matched. Otherwise, the empty string is returned.


Syntax:

regexp_extract(DataFrame_obj.String_Column, pattern, index)


The first parameter is the column which is of string type where the search is performed on this column.
The second parameter is the pattern where the string is extracted based on the specified pattern.
The index specifies the part of the match where we need to extract from the group of matches.



The “r'(\d+)’” is the pattern that extracts the digits from the string.
or
 The regular expression "\\d" is used to match any digit.


# Extract digits
emp_df.select(regexp_extract(emp_df.Address, r'(\d+)', 1).alias('EMP PHONE')).show()





 extract the first capital alphabet string by specifying the pattern – “([A-Z]+)”.
 We extract the first lower alphabet string by specifying the “([a-z]+)” pattern.


# Extract Uppercase alphabet
emp_df.select(regexp_extract(emp_df.Address, '([A-Z]+)',1)).show()

# Extract lowercase alphabet
emp_df.select(regexp_extract(emp_df.Address, '([a-z]+)',1)).show()



Extract the Employee’s First Name

To extract the first name of the employee, the pattern that we specify is “(\w*)”. This extracts the characters until the space occurs.


employee_df.select(employee_df.Employee_details,regexp_extract(employee_df
.Employee_details, "(\w*)", 1).alias("EMPLOYEE FIRST NAME")).show(truncate=False)



Extract the Employee’s Last Name
To extract the last name of the employee, the pattern that we specify is “() (\w*)”.



To extract the employee’s country, the pattern that we specify is “(\w*) (\w*$)”.
employee_df.select(employee_df.Employee_details,regexp_extract(employee_df
.Employee_details, "(\w*) (\w*$)", 1).alias("EMPLOYEE COUNTRY")).show(truncate=False)


To extract the employee’s contact, the pattern that we specify is “(\d*$)”.  To extract the digits, the character “d” is used and “*” matches zero or more occurrences in the pattern. The “$” is used to match the end of the string.

Q. cron jobs
A cron job is a scheduled task or automated script that runs at specified intervals on a Unix-like operating system.


Cron Tab:

The scheduling information for cron jobs is stored in a file called the "cron tab" or "crontab."

Crontab Syntax:

The crontab syntax consists of five fields that define when a job should run: minute, hour, day of the month, month, and day of the week.

minute hour day month day_of_week command_to_run


Common Symbols in Crontab Syntax:

* (asterisk): Represents any value. For example, * in the minute field means "every minute."
*/n: Specifies intervals. For example, */5 in the hour field means "every 5 hours."
1,2,3: Specifies a list of values. For example, 1,15 in the day field means "on the 1st and 15th day of the month."
Editing the Crontab:

To edit the crontab, you can use the crontab command. For example, to edit the current user's crontab, you can run:

crontab -e
This opens the crontab file in the default text editor (usually vi or nano).



----------------------------------------------------------
Examples:

Run a script every day at midnight:

bash
Copy code
0 0 * * * /path/to/your/script.sh
------------------------------------------------------------

Run a command every 15 minutes:

bash
Copy code
*/15 * * * * /path/to/your/command
Run a command every Monday at 3:30 PM:

bash
Copy code
30 15 * * 1 /path/to/your/command
Viewing Crontab:

To view the current crontab, you can use the following command:

bash
Copy code
crontab -l
This displays the current user's crontab entries.

Q.
what are the slowly changing dimensions

A slowly changing dimension (SCD) is a dimension that stores and manages both current and historical data over time in a data warehouse.

there are several different types of SCD

Q.
what are the types of SCD 

there are 6 types of slowly changing dimension



type0
(Fixed dimension)
No changes allowed, dimension never changes


example
source table(employe table)

e_id	e_name	e_desig		e_sal	e_loc

101	lacky	developer	5000	hyd
102	mas	admin		3500	sec

whenever load data our source table to base table(our hadoop environment) this data comes to as same
(no changes allowed, dimension never changes, our table remains the same. this means our existing data will continue to show the same figure)

base table (after loading the data no changes allowed)(if you update  any record it shown as same as source data in base table)
(note:before loading the data the source table is change)

e_id	e_name	e_desig		e_sal	e_loc

101	lacky	developer	5000	hyd
102	mas	admin		3500	sec





type1
(No history)
update record directly, there is a no record of historical values, only current state
note: disadvantage is there is a no maintain the old data


source table(employe table)

e_id	e_name	e_desig			e_sal		e_loc

101	lacky	sr.developer(update)	7000(update)	hyd
102	mas	admin			3500		sec


base table 

e_id	e_name	e_desig		e_sal	e_loc

101	lacky	sr.developer	7000	hyd
102	mas	admin		3500	sec



type2
(row versioning)
track changes as version record with flag & current, previous date columns 



source table(employe table)

e_id	e_name	e_desig			e_sal		e_loc

101	lacky	sr.developer(update)	7000(update)	hyd
102	mas	admin			3500		sec


base table

sarrogate_key	e_id	e_name	e_desig		e_sal	e_loc 	effective_from 	effective_to 	flag
	1	101	lacky	sr.developer	7000	hyd	01-02-2024	04-05-2024	1
	2	101	lacky	developer	5000	hyd	01-02-2000	31-01-2024	0-------->this means old record
	3	102	mas	admin		3500	sec	01-01-2000	01-01-2022	1



in this type2 added 4 columns 
one is sarrogate_key this is added sequence number each every row
and effective_from, effective_to which is added to the starting date and ending date 
and another one is flag in the flag is 0 that menas identify the old record, if the flag is 1 the record is latest record


note: disadvantage is per suppose daily millions of record updates so the data size is increased and performance is dicreased

(mostly we are used type2)



type3
(previous value column)
track changes to specific attribute, add a column to show the previous value, which is updated as further changes occur

there is no add the sarrogate column and effective date from and effective date to and no add the flag
it is only add the column of previous and present which is update the attribute of column.

Q.

What is a Stored Procedure?
A stored procedure is a prepared SQL code that you can save, so the code can be reused over and over again.

CREATE PROCEDURE SelectAllCustomers
AS
SELECT * FROM Customers
GO;

EXEC SelectAllCustomers;



CREATE PROCEDURE SelectAllCustomers @City nvarchar(30)
AS
SELECT * FROM Customers WHERE City = @City
GO;

EXEC SelectAllCustomers @City = 'London';

Stored Procedure With Multiple Parameters
Setting up multiple parameters is very easy. Just list each parameter and the data type separated by a comma as shown below.

CREATE PROCEDURE SelectAllCustomers @City nvarchar(30), @PostalCode nvarchar(10)
AS
SELECT * FROM Customers WHERE City = @City AND PostalCode = @PostalCode
GO;

EXEC SelectAllCustomers @City = 'London', @PostalCode = 'WA1 1DP';

3.
view

In SQL, a view is a virtual table based on the result-set of an SQL statement.

The fields in a view are fields from one or more real tables in the database.


if the data were coming from one single table.

A view is created with the CREATE VIEW statement. 

CREATE VIEW [Brazil Customers] AS
SELECT CustomerName, ContactName
FROM Customers
WHERE Country = 'Brazil';



SQL Updating a View
A view can be updated with the CREATE OR REPLACE VIEW statement.

CREATE OR REPLACE VIEW [Brazil Customers] AS
SELECT CustomerName, ContactName, City
FROM Customers
WHERE Country = 'Brazil';


DROP VIEW view_name;




Creating View from multiple tables

CREATE VIEW MarksView AS
SELECT StudentDetails.NAME, StudentDetails.ADDRESS, StudentMarks.MARKS
FROM StudentDetails, StudentMarks
WHERE StudentDetails.NAME = StudentMarks.NAME;

The following constraints are commonly used in SQL:

NOT NULL - Ensures that a column cannot have a NULL value
UNIQUE - Ensures that all values in a column are different
PRIMARY KEY - A combination of a NOT NULL and UNIQUE. Uniquely identifies each row in a table
FOREIGN KEY - Prevents actions that would destroy links between tables
CHECK - Ensures that the values in a column satisfies a specific condition
DEFAULT - Sets a default value for a column if no value is specified
CREATE INDEX - Used to create and retrieve data from the database very quickly

AWS EC2 Instance Types
Different Amazon EC2 instance types are designed for certain activities. Consider the unique requirements of your workloads and applications when choosing an instance type. This might include needs for computing, memory, or storage.

The AWS EC2 Instance types are as follows:

General Purpose Instances
Compute Optimized Instances
Memory-Optimized Instances
Storage Optimized Instances
Accelerated Computing Instances
1. General Purpose Instances
It provides the balanced resources for a wide range of workloads.
It is suitable for web servers, development environments, and small databases.
Examples: T3, M5 instances.

2. Compute Optimized Instances
It provides high-performance processors for compute-intensive applications.
It will be Ideal for high-performance web servers, scientific modeling, and batch processing.
Examples: C5, C6g instances.

3. Memory-Optimized Instances
High memory-to-CPU ratios for large data sets.
Perfect for in-memory databases, real-time big data analytics, and high-performance computing (HPC).
Examples: R5, X1e instances.

4. Storage Optimized Instances
It provides optimized resource of instance for high, sequential read and write access to large data sets.
Best for data warehousing, Hadoop, and distributed file systems.
Examples: I3, D2 instances.

5. Accelerated Computing Instances
It facilitates with providing hardware accelerators or co-processors for graphics processing and parallel computations.
It is ideal for machine learning, gaming, and 3D rendering.
Examples: P3, G4 instances.

Type of S3 storges:
===================
s3 storge types based on 3 things:

1) Availability
2) Duarability
3) Pricing

Standard:
 Suitable for frequently accessed data, that needs to be highly available and durable.


Standard Infrequent Access (Standard IA):
 This is a cheaper data-storage class and  this class is best suited for storing 
infrequently accessed data like log files or data archives


Intelligent Tiering: 
This service class classifies your files automatically into frequently accessed and infrequently accessed and
 stores the infrequently accessed data in infrequent access storage to save costs. 
This is useful for unpredictable data access to an S3 bucket

One Zone Infrequent Access (One Zone IA): 
-->All the files on your S3 have their copies stored in a minimum of 3 Availability Zones. but
-->One Zone IA stores this data in a single availability zone. 
-->It is only recommended to use this storage class for infrequently accessed, non-essential data. There may be a per GB cost for data retrieval.


Reduced Redundancy Storage (RRS):
 All the other S3 classes ensure the durability of 99.999999999%. RRS only ensures 99.99% durability. AWS no longer recommends RRS due to its less durability. However, it can be used to store non-essential data.

    arn:aws:<service_name>:<Region_code>:<Account>:

what is datacatalog

persistent technical metadata store

can connect to 70 different sources and manage your data in centralized data catalog


The AWS Glue Data Catalog is a centralized metadata repository provided by AWS Glue. 
persistent technical metadata store and manage data across different data sources. 
The Data Catalog stores information about the location, schema, format, and structure of data stored in databases, data lakes (like Amazon S3), or other storage systems.

Here are the key features of the AWS Glue Data Catalog:

1. Metadata Management:
The Glue Data Catalog holds metadata (e.g., table definitions, column types, and data locations) for your datasets. Each dataset is represented as a "table" in the catalog.
It supports many sources such as Amazon S3, RDS, Redshift, and DynamoDB.
2. Schema Discovery with Crawlers:
Glue Crawlers are used to automatically discover and classify data. They scan your data sources, identify the format, infer schemas, and populate the Data Catalog with this metadata.
You can configure crawlers to run on a schedule to ensure your metadata stays up to date as your data evolves.
3. Partitioned Data Handling:
The Glue Data Catalog supports partitioned data (such as partitioned tables in Amazon S3), enabling faster queries and ETL jobs by accessing only relevant partitions.
4. Integration with AWS Analytics Tools:
The Glue Data Catalog integrates with various AWS services like Amazon Athena, Amazon Redshift Spectrum, and Amazon EMR, making it possible to query and analyze the data using SQL-like queries.
With Amazon Athena, for example, you can query data in S3 using SQL based on the metadata in the Glue Data Catalog.
5. Versioning and Schema Evolution:
The Data Catalog supports schema versioning, which helps in tracking changes over time. If your data schema evolves (e.g., adding or removing columns), you can manage the different versions within the catalog.
6. Tagging and Searchability:
You can tag your tables and databases with metadata tags, making it easier to search, categorize, and manage your data assets.
7. Access Control:
AWS Identity and Access Management (IAM) policies can be applied to control access to the Glue Data Catalog. You can define which users or roles have access to specific metadata or data resources.
Use Cases:
Data Discovery: Helps in searching and discovering datasets quickly using the metadata it stores.
Data Governance: Facilitates data governance by providing a central repository for metadata.
Data Sharing: The Data Catalog simplifies sharing metadata across teams and AWS accounts for collaborative data analysis.
In summary, the AWS Glue Data Catalog is a critical component for managing and discovering data efficiently, especially in environments where data is distributed across various services and formats. It plays a key role in supporting ETL, analytics, and data lake solutions on AWS.

Databases

a glue database is a logical container within the aws glue data catalog that store metadata tables

these tables contains information about data stored in various sources such as amazon s3, amazon rds, amazon redshift, and more

the glue database helps organize and manage metadata, making it easier to catalog, search, and query your data assets.

not a physical database

----------------------------
tables

object within the aws glue data catalog  that defines the schema and properties of a dataset

tables store metadata about the actual data stored in various data sources such as amazon s3, amazon redshift , and othrs

aws glue tables play crucial role in organizing , quering and transforming data by providing a structured wayh to describe and access data

not a physical table-data doesn't move -it stays in the sources (s3/rds etc)

----------------------------

crawlers

crawler is a program that connects to the data source and automatically scans in various data sources to determine its schema and create metadata tables in the aws glue data catalog

----------------------------
connections

an aws glue connections is a configuration object  that enables aws glue to connect to your data sources 

it contains the necessary connection details such as the database endpoint, username and password,
which aws glue uses to establish a connection to data sources like amazon rds, amazon redshift or other jdbc-complaint database
